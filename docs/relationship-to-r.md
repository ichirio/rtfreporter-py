# Relationship to the R package

`rtfreporter` for Python is a **port**, not an independent project. It exists to
give Python users the same clinical RTF reporting toolkit that the
[R package](https://ichirio.github.io/rtfreporter/) provides, with the same
function names, the same arguments, and the same output.

## How this project is developed

!!! info "Features land in R first"

    **New functionality is designed and implemented in the R package, and then
    ported to Python.** The Python package does not add features of its own.

    This keeps the two implementations from drifting apart: there is one place
    where a feature's behaviour is decided, one place where it is specified, and
    the Python side follows.

What that means in practice:

| If you want to… | Where it happens |
|---|---|
| Propose a **new feature** | The R package — it is designed and built there first |
| Report a **Python-only bug** (a port defect) | [rtfreporter-py issues](https://github.com/ichirio/rtfreporter-py/issues) |
| Report a bug in the **shared behaviour** | The R package, since the fix originates there |
| **Ask a question** or discuss usage | [Discussions on the R repository](https://github.com/ichirio/rtfreporter/discussions) |

### Discussions are shared with the R package

There is **one Discussions forum for both packages**, hosted on the R
repository:

<div class="grid cards" markdown>

- :fontawesome-solid-comments: **[rtfreporter Discussions](https://github.com/ichirio/rtfreporter/discussions)**

    Questions, usage help, and design conversation for **both** the R and the

Keeping one forum means an answer about pagination, borders or headers helps
users of either package, rather than being written twice and diverging. The
Python repository keeps its own **issue tracker** for defects specific to the
port.

## What "a faithful port" means here

The Python package deliberately mirrors the R one:

- **Every exported R function outside the ARD / plan layer exists in Python**
  (R 0.8.2.9026; see *Current parity* below) under the same names —
  `rtf_border_line()`, `rtf_document()`, `generate_rtfreport()`,
  `as_rtftables()`, `assemble_rtf()`, and so on.
- **Argument names, order and defaults follow R**, so R documentation and
  existing R code translate almost literally.
- **Output is compared against R.** The showcase tables assert their figures
  against numbers generated by the R package — see
  [Demographics](showcase-dm.md#validation-against-r) and
  [Adverse events](showcase-ae.md#validation-against-r).

There are two deliberate departures, both for Pythonic ergonomics; they are
described on [Differences from the R package](r-differences.md).

!!! note "Scope: the R package's ARD / plan layer is not ported"

    The R package is gaining a table-planning layer — `table_plan()`, the
    `plan_*()` verbs, `plan_apply()`, `plan_template()` — and an ARD family
    — `normalize_ard()`, `widen_ard()`, `pull_ard()`, `list_ard_keys()`,
    `cell_rows()`, `overall_row()`. These are **intentionally not ported**:
    they consume `cards` / `cardx` analysis results data, which exist only
    in R. The "every R export exists in Python" statement above refers to
    the rendering toolkit and does not include this layer.

## Where the two packages necessarily differ

The R package's headline feature is reading **table objects from the wider
pharmaverse** — `gt`, `gtsummary`, `rtables`/`tern`, `tfrmt`, `flextable`,
`huxtable` — and turning any of them into RTF. That is a statement about the R
ecosystem, and it does not carry over: **those packages have no Python
equivalents.**

So the two projects have different centres of gravity:

| | R package | Python package |
|---|---|---|
| Core idea | Read **any** R table object and render it to clinical RTF | Provide the **same toolkit and output** to Python users |
| Table sources | gt, gtsummary, rtables/tern, tfrmt, flextable, huxtable, data.frame | pandas, polars, `great_tables` |
| Worked examples | The same report built through six different frameworks | The same report built from a DataFrame and from `great_tables` |

This is an ecosystem limitation, not an unfinished port: there is no Python
`gtsummary` to read. Where a Python analogue exists — `great_tables` is the
Python port of `gt` — it is supported in full, including spanners, cell styles
from `tab_style()`, row groups, summary rows and footnotes. See
[Importing tables](importing-tables.md).

## Current parity

| Area | Status |
|---|---|
| Followed R version | <span class="rtf-badge ok">0.8.2.9026</span> the R development version after the v0.8.2 release (`main` at 2385a6b), which this port matches |
| Exported functions | <span class="rtf-badge ok">93 / 94</span> every R export outside the ARD / plan engine (125 exports, 31 of them ARD / plan), except `rtfreporter_ai_manual()` (the R package's AI-assistant manuals, which describe the R API); `tests/test_api_parity.py` checks it |
| Renderer, pagination, borders, styling, listings, figures, assembly, run tokens | <span class="rtf-badge ok">ported</span> — checked byte-for-byte against R 0.8.2.9026 |
| Table-object adapters | <span class="rtf-badge partial">pandas, polars, great_tables</span> — the R-only frameworks have no Python counterpart |
| ARD / plan layer (`table_plan()`, `plan_*()`, `normalize_ard()`, …) | <span class="rtf-badge partial">not ported</span> — by design; it consumes `cards` / `cardx` data that exist only in R (to be reconsidered when the Python package is used in earnest) |

How the parity is checked: the differential harness in `data-raw/xcheck/`
renders the same cases with both packages and requires byte-identical RTF
(see its README); the R side's output is committed, so CI enforces it without
R installed.

## Versioning

The two packages version **independently**. The Python package's version says
nothing about which R version it corresponds to; consult the
[changelog](https://github.com/ichirio/rtfreporter-py/blob/main/CHANGELOG.md)
for what a given release contains.
